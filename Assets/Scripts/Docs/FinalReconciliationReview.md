## 3. Cross-pass consistency — checked, no behaviour change needed

Each item below was checked in the actual Pass 1 to Pass 5 files and
review docs in this worktree, not from summaries alone. Where the
passes agree, that agreement is recorded so a later reader does not
have to re-derive it. Where they deliberately leave a question open,
that openness is recorded as consistent, not as a contradiction.

- Bakery model: CONSISTENT. Pass 2 chose the shop runtime
  (PlanBatch / WorkDay, used by the slice runs) as the surviving
  production model, with the staged 9-step chain reaching customers
  only through `Pass2BakeryStagedTransfer` plus
  `BakeryShopRuntime.ReceiveTransferredBreadLot`. Aging is preserved
  from the BAKED day: a loaf baked yesterday is day-old when
  transferred today, never fresh again; stale staged lots are
  refused, failed transfers leave staged stock intact. Pass 3
  wholesale intake (`Pass3WholesaleIntake`) uses the SAME rule
  explicitly: condition derived from baked day vs transfer day,
  fresh same day, day-old next day, stale after more than one day
  and refused, transfer day before baked day refused. Pass 4 and
  Pass 5 do not introduce a second bakery model. The only open
  bakery question is the one Pass 2 flagged: transfer-day aging
  instead of baked-day aging, if Kennedy wants it — a single place
  to change, not a divergence.

  production. Pass 3's `Pass3PerItemOffer` is a tested MODEL that
  returns exactly one item's line for a multi-item category, never
  an aggregate mislabelled as flour or bread. Pass 3 states
  explicitly that the production trading port
  (`GeneralStoreRuntimeManager.BuildHouseholdTradingPort`, single-item
  guard) is NOT edited in Pass 3, so the production shopping-loop
  block for `staple_food` (7 items: flour, bread, potatoes, salt,
  sugar, coffee, tea) REMAINS until Codex wires an adapter to the
  per-item model. No later pass claims otherwise. The decision

  still open, see section 7.
