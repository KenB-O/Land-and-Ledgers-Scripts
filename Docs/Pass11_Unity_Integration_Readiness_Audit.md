## 2 - Four harness-excluded files, inspected in depth

### Method and headline result

Two Roslyn builds were run from the audit worktree, both with isolated outputs under /tmp and with no repo files changed.

- Harness-subset variant - the harness sources plus the four files (with the SharedBusinessRuntimeManager exclusions removed and Orchestration/Systems and Domains/Civic added). Result - 112 errors, every one a missing type that exists in the repo in a directory outside the harness subset. Conclusion - the harness-subset errors are a subset artifact, not source defects.
- Full-repo Roslyn build - every .cs file except non-test Editor folders, 1154 files, plus the harness UnityEngine, UnityEditor and NUnit shims. Result - 1358 error lines, all CS0246 or CS0234, and zero in any of the four files. The bulk are Unity package types the shims do not provide (TextMeshPro types, UI Button and Canvas, InputSystem Keyboard and Key, Terrain and TerrainData, SceneManagement, UnityTest attributes). Conclusion - under a full source set the four files have no confirmed Roslyn compile defect. That narrows PASS9-014 considerably, but it does not close it. Real Unity compilation still needs the real UnityEngine and package assemblies, real scene serialization, and the real .NET profile Unity targets, none of which a Roslyn shim build reproduces.

No missing type reference, wrong method signature, invalid constructor call, obsolete overload, missing namespace import, or duplicate registration was confirmed in the four files. The defects below are the real findings from reading them, split by fix class. S means fixable in source on this machine. U means it needs a Unity Editor session or scene access.

## 3 - Scenario start and objectives wiring

Three scenario-goal stores exist and they are not the same store.

- ScenarioService.ActiveState - the asset-based Director path. ScenarioStartPanelController.StartScenario calls ScenarioDirector.SwitchScenario, which calls ScenarioService.BeginScenario, bootstraps the player household and enqueues starting tasks. FirstLedgerBootstrap and SaloonCircuitBootstrap subscribe their goal evaluators to SimulationDrivers.OnScenarioTick (multicast, with a Unity Test Runner test proving two subscribers survive). OnGoalCompleted forwards to ScenarioDirector.RecordLiveGoalCompletion, which the puppet master panel reads. This path is live provided the scene holds the panel, the director, the registry assets and the bootstraps. Scene presence cannot be verified from here, so it stays Unity-Editor verification.
- ScenarioObjectiveService - the hub-owned dated-qualifier path. SimulationSystemsHub constructs it and round-trips its ScenarioRunState through SystemsSaveDto.scenarioRunState, but no production code calls BeginScenario or Evaluate. ScenarioBootstrapFactory.TryCreateStart has zero production callers, so the Pass IX handoff line about calling the factory from the start panel is stale for the Director path and still true for this path. Nothing registers the Saloon Circuit dated qualifier from live goal state.
- Evaluator CompletedGoalIds - FirstLedgerBootstrap.CaptureSaveDto overwrites the director DTO completedGoalIds with the evaluator list, and RestoreFromSaveDto restores the evaluator from the same DTO. So a save carries director goals, evaluator goals and hub latched goals through three different fields.

Consequences, each a finding in section 9.

- After a load, the dated qualifiers list is empty because qualifiers are Func predicates and are never persisted. LoadRunState restores latched and failed ids but no qualifier, so Evaluate becomes a no-op until something re-registers qualifiers. No production code does that re-registration.
- ScenarioObjectiveService.Evaluate latches a goal whenever its predicate holds at any evaluation, including an evaluation after the deadline. The code checks the deadline only on the failure branch, so a goal first observed as met after its deadline latches complete instead of failing. The doc comment describes latching for predicates holding on or before the deadline. Code and comment disagree, and the code is the lenient one. This is a player-facing deadline defect, not a crash.
- ScenarioRunStateEvents.ScenarioFailed has zero subscribers in production, so a scenario failure persists but nothing notifies the player or any UI.
- ScenarioObjectiveService.BuildHeadlineSnapshot reads the deadline from the qualifiers list, so after a load (empty qualifiers) the headline deadline is -1 even when the run state knows the scenario id.

## 4 - Freight runtime registration

Registration is manager-driven, not scene-driven, for manager businesses.

- SimulationDrivers.DriveFreightCompanies runs daily from DrivePostalRevenue. For each BusinessInstanceState of type LiveryFreight it calls EnsureFreightCompany, which calls FreightProductionDriver.EnsureCompany with the business instance id and runtime state. EnsureCompany keys companies by instance id in a dictionary, so a second call for the same business reuses the instance instead of duplicating it.
- The handler for AdvanceTick resolves from the carrier owner person id first, then from the first active employee of the carrier, then EntityId.Invalid. AdvanceTick still runs with an Invalid handler. Whether an Invalid handler degrades dispatch, wage attribution or diagnostics is a verification item for WS2, not a confirmed defect.
- Every live business runtime is registered with the driver on the same daily drive (RegisterBusinessRuntime) so each shipment payer resolves to its real till for verified collection. Unresolvable payers stay uncollected with no credit and no legacy fallback (Pass IX R-04).
- The remaining Unity question is narrow. If the scene also places FreightCompanyRuntime instances independently of manager businesses, WS2 must confirm they are the same instances EnsureCompany returns and not a second set. If the scene places none, the handoff item is already satisfied for manager businesses and only the PlayMode end-to-end delivery proof remains.

## 5 - Housing, boarding and household moves

- HousingAuthority is the live authority. DriveTenancyPayments settles due rents daily through the hub HousingAuthority, household ledgers, the live tenancy payee directory, the obligation authority and the id registry. DriveHousingAbsenceSweep ends occupancies of the absent daily with the lenient-arrangement predicate.
- Boarding registration is live but narrow. FirstLedgerSliceBootstrapper registers a BoardingHouseShopRuntime per BoardingHouse business with authored bed capacity above zero, through SimulationDrivers.RegisterBoardingHouseRuntime into SimulationSystemsHub.RegisterBoardingHouseRuntime, which dedups by reference. DriveBoardingHouseDays and DriveBoardingHouseWeeks then execute the runtimes daily and weekly, with weekly dues settled through RentCollection. A boarding business with zero authored bed capacity is skipped with a warning and never gets a runtime. Bed capacity is therefore a silent gating input that WS2 must surface in diagnostics or authoring checks.
- HouseholdMoveService is confirmed caller-free in production. Occupancy changes in production go through HousingAuthority directly (acquisitions, tenancies, estate and absence paths), never through the service all-or-nothing move operation. That means the validated-before-mutation, no-partial-move guarantee the service provides does not cover live moves. Either a production caller must be chosen for the paths where a whole-household move is the right operation, or the registry entry must be reclassified as intentionally dormant with the direct paths documented as the live move mechanism.

## 7 - Banking bindings, civic registration and schoolhouse term boundaries

- Cash-store binding is live for NPC businesses and households. SimulationDrivers.WireNpcBusinessCashStores registers business-prefixed instance id stores through NpcBusinessRuntimeCashPort, and RefreshHouseholdCashBindings registers household-prefixed id stores through HouseholdCashStore, but only for ledgers that already exist in the authoritative registry (it deliberately refuses to manufacture an empty ledger to expose a finance window). Construction, lending and distress-sale paths that consume CreditCash therefore resolve real stores for those owners.
- Bank-business binding is missing. No production code constructs BankRuntime or registers a BankDepositLedger as a CreditCash store. PlayerDebtManager underwriting and the Pass IX handoff item (bind bank ledger scene objects for player-owned banks so player tax and lending legs display against the same stores the source drives) are both still open, and RUN-003 (live bank deposit refresh before underwriting) stays open. BankRuntime is also the thirteenth unwired detailed runtime (see section 8).
- Civic registration is live. CivicTreasuryService is hub-owned with measured credit legs for player and NPC tax payment, and NpcPropertyLifeService holdings register at the acquisition closing, levy once per tax year and persist in NpcPropertyLifeSaveDto.
- Schoolhouse term boundaries are the open question. SchoolhouseAssignment defines a term as 60 day-aligned blocks from day 0 (TermStartFor returns day minus day modulo 60, term wage 12000 cents at 200 cents per day). SimulationDrivers.DriveSchoolhouseTeacherPay fires only on term-start days by that rule, finds CivicFoundationManager in the scene, reads its Schoolhouse state and calls PayTeacher, which settles exactly once per term (treasury debit equals household credit plus at most one shortfall Payable, with a no-ledger refusal and a compensating rollback). Two fragilities remain. First, teacher assignment itself refreshes inside CivicFoundationManager snapshot refresh (RefreshSchoolhouseFromWorldAndPopulation, called from RefreshFromWorldInternal on Awake and on snapshot reads with a per-frame cache), so assignment is readout-driven rather than tick-driven and the state PayTeacher sees depends on whether a readout happened. Second, the scene term boundaries the Pass IX handoff mentions are not defined anywhere in source, so a scene that thinks in calendar terms and a driver that thinks in 60-day blocks can disagree about when a term starts. WS1 must either move the call into a scene term flow or record the 60-day block rule as the single term authority.

Partially overlapping means the detailed model shares helpers or state with a live path. ## 9 - RealDemandSource, exact intended role

RealDemandSource is a collection-side replacement for the retired town-pulse revenue path, not an executor and not a read model for display.

- What it does - CollectDemand builds PurchaseIntents from real household needs (through HouseholdNeedRegistry and household ledgers) and registered business input needs, each naming a real buyer, a real stocked supplier at a valid price and documented provenance. Collection never moves money or goods. BusinessInstanceSellerAdapter implements the supplier side over a live BusinessInstanceState.
- What it does not do - it never buys anything. The TownWorld purchase path and the embodied shopping path resolve demand themselves when purchases happen. SharedBusinessRuntimeManager exposes CollectRealDemand and RegisterBusinessInputNeed wrappers, but neither wrapper has a production caller outside the manager file. Tests are the only callers.
- Decision required (PASS9-008, P2) - either build a real intent executor behind it that routes each intent through the production sale authorities (the same authorities the embodied shopping path uses, never a new money path), or retire the type and delete the wrappers. Wiring collection without an executor would fake execution (intents collected, nothing bought), which is exactly why Pass IX registered it honestly unwired. The executor design must also answer who re-collects after a failed intent, whether an intent survives save and load (intents are currently not persisted), and whether business input needs registered by unwired runtimes are ignored until those runtimes are wired.

- Freight in and out - Connected. ReceiveFreightIntoDestinationStock measures destination stock and refuses without a live destination runtime. Freight revenue settles only on truly delivered shipments.
- Split - Connected with one defect. HouseholdInventory.SplitLot and MineOreStock SplitLot conserve quantity, but MineOreLot.CreateSplit duplicates the assayed flag and assayId to the child, so one assay certifies two lots (PASS9-005, P3).
- Merge - Connected. HouseholdInventory.MergeCompatibleLots and MineOreStock MergeCompatibleLots conserve quantity. Assayed lots can never re-merge, which is a deliberate guard, not a bug.
- Consume - Connected for daily needs (embodied consumption through real stocks) and partial for interiors (bulk consumption inside business interiors has no per-lot record until the IDENT-001 phased migration reaches that domain).
- Loss and destroy - Connected for shipments (refusal holds as Delayed, never false-delivers) and partial elsewhere. Sawmill surplus after an outlet sale is re-stored or recorded as disposed mill fuel. A general loss and destroy ledger across domains does not exist, and WS3 should confirm whether Canon requires one before building it.

Campaign-scale save and restore profiling (PASS9-013) remains a P4 measurement item.
